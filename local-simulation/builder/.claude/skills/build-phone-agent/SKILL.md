# Build a phone agent from a brief

You are given one or more brief documents and one tool API file. You produce one workflow file. Work from this folder. Finish inside 8 minutes: write `rules.md` and `gen.py` in few, large steps.

Work only inside the current folder: the documents you were given, `docs/`, `reference/` and `check_workflow.py`. Do not look for, read or copy any other agent, generator or output from anywhere else on this machine: an agent built for another brief carries that brief's rules. Write `rules.md` and `gen.py` yourself from the documents.

Every rule, sentence, number, name and allowed value in the workflow must come from the documents you were given and from the tool API file. Nothing in this skill or in `reference/` is a rule of the bank.

## How a call is scored

One simulated customer passes only when all three hold. There is no partial credit, and the same customer is run three times and must pass all three.

1. **The bank's records are right.** A program compares the bank's ledger with the expected one: the closing outcome and reason, the exact set of promises (product, amount, date), notes, callbacks and transfers. The last tool call must be the closing call. The bank does not enforce the brief: it accepts a promise on a holiday or below the minimum. Keeping the rules is the phone agent's job.
2. **A judge model reads the transcript against 2 to 4 checks written for that customer.** The judge does not see the brief. It sees the numbered transcript, every tool call with its arguments and result, every step change, and how the call ended. It trusts those events over what was said. Checks are of these kinds: an order ("no X before identity is verified"), a count ("asked exactly once", "one tool call per product"), a required sentence, a forbidden word or offer, honesty after a failed tool.
3. **The call ends properly.** The judge fails a call that ends on a timeout, that repeats lines after the conversation is over, or that keeps talking until a limit stops it.

What this means for the design:

- The judge reads literally. If the brief forbids a word before some event, that word must not appear in any sentence the agent can say before the event, in any form or meaning. If a tool can fail, words such as "recorded", "scheduled", "transferred", "confirmed" must not be spoken before that tool has returned success, not even in an unrelated sentence. Choose other wording for early sentences. This includes sentences the brief itself requires early: when the brief demands an early statement that contains such a word (for example that the call is recorded) and also restricts that word until a tool has succeeded, say the early statement with another form of the word ("we are recording this call"). The platform's judge has failed calls for exactly this.
- The judge counts. "Ask once" means the question appears once in the transcript. Repeating your own question after the customer asked something back counts as a second ask. Count with variables, not with the model's memory.
- A required sentence must be complete and inside one agent message. Use the brief's own words for it.
- A tool call that runs twice is seen twice. Set `maxRetries` to 0 on tools that write to the bank and decide retries yourself.
- No excuse is accepted: a rule broken because a tool failed is still broken.

## The simulated customer

The customer is a model that follows a short script. It knows its name, its security answers and its script. It does not know the debt or the date. Its fixed rules: it answers what it is asked and does not volunteer; it says "Yes, I confirm." when a read-back matches; when the agent says goodbye it says "Thank you, goodbye." and then says nothing more.

- **After the agent's goodbye the customer is silent.** A call that is still open then dies on a timeout and fails. So the goodbye, the closing tool call and the end of the call must happen in one engine-driven chain with no customer turn in between. Never say "goodbye" earlier.
- Customers vary in how they talk. Build for all of these: a number or date given in two parts across turns; a value said wrong and corrected in the same sentence (the last value counts, also for security answers); a talkative customer who mentions an unrelated date and gives facts before being asked; a customer who asks a question back before answering (answer it shortly, then wait: do not repeat your own question); amounts and dates said in words, codes said digit by digit; a turn cut off mid-sentence (do not call a tool with half a value; say what you heard and ask for the missing part).
- Each customer carries one trap: a wrong security answer, a relative on the line, a date past the limit or on a holiday, a vague period, an amount below the minimum, hardship, a dispute, "already paid", a request the agent may not grant, a tool that fails on its first call. Read the brief for every such branch and build each one.

## Steps

1. Read every brief document, then the tool API file. If there are several documents, a later or more specific one overrides an earlier one where they disagree (a memo changes a policy; an extension brief changes its base brief).
2. Read `docs/workflow-format.md` and `docs/tools-and-code.md` in full. Read `reference/base-agent.json` for the JSON shapes.
3. Write `out/<slot>/rules.md`: every rule of the brief on its own numbered line, each with the mechanism that will enforce it (see the table below) and the step it lives in. Include the closing table (every outcome and reason and what leads to it), every required sentence word for word, every forbidden word or offer and until when, every limit and count, the calendar rules, and every tool with its fields and allowed values. A rule that is not in this file will not be in the agent. When the file is written, run `python3 check_rules.py <every brief document> --rules out/<slot>/rules.md`: it lists every quoted sentence and every quantity of the brief (a time of day, a percentage, an amount, "two wrong answers", "the 8th working day") that it does not find in `rules.md`. Go through the list once. Add what is a rule; leave what is only an example or what a later document has replaced. Two kinds of lines are easy to lose, so write them separately:
   - **Every exception inside a rule gets its own line** ("unless", "if the customer still ...", "this rule comes before rule N", "except"). An exception is a path of its own in the workflow: say which variable or extracted value takes the call onto it. A branch that closes the call must not be reachable when its exception applies.
   - **Every count gets its own line**: anything the brief limits or counts (a question asked once or twice, wrong answers, attempts, an offer made once, a sentence said once, a retry). For each: the counter variable, the engine event that changes it, and the transition that reads it. See "Counts, single offers and closings" below.
4. Write `out/<slot>/gen.py`: a Python program (standard library only) that builds the workflow as a dict and writes `out/<slot>/workflow.json`. Keep the brief's values in constants at the top. Keep everything the brief computes, counts or reads in ONE Python library text that every code step shares, as plain functions that take their inputs as arguments and return a value (no reading of call variables inside them): the calendar (working day, earliest day, each deadline, what a named day or a relative day resolves to), every minimum and band, reading a date, a time, an amount or a number as the customer says it, and which closing outcome and reason follow from which end state. The code steps call these functions; they do not repeat the arithmetic.
4b. Write `out/<slot>/selftest.py` and run it with `python3 out/<slot>/selftest.py`: it loads that library text out of `gen.py` (give `gen.py` an `if __name__ == "__main__":` guard so it can be imported) and holds one assertion for every line of `rules.md` that computes, counts or reads something, named with the rule's number. Work the expected value out by hand from the brief, not by running the code; use the brief's own worked examples first, then the edges: the last allowed day and the day after it, a time exactly at a limit and one minute past it, an amount at a minimum and just below it, a call on the day before a non-working day, the same value said in the other ways a customer says it. 30 to 60 assertions, at most 6 KB, no model, under two seconds. It prints each failed assertion with its rule number and exits with 1. A failed assertion means the library does not do what `rules.md` says: fix the library. Change an expected value only when the brief shows that your hand calculation was wrong. This file is run again by the program that started you after every repair, so a later change cannot silently undo a rule. Build every conversation step through ONE helper function of your own, so that what every step needs (the `side_q` extraction and the `broken_off` member, see below, and their transitions) is added in one place and cannot be forgotten in a step. Run it.
5. Run `python3 check_workflow.py out/<slot>/workflow.json <tool_api_file>` and fix every ERROR. Read each warning and fix it or decide it is intended. The check refuses, among other things: a hook that empties a call's url, code that writes a value outside an extraction variable's enum, a conversation step without a `broken_off` member, and a conversation step without a `side_q` extraction.
6. Run `python3 fuzz_workflow.py out/<slot>/workflow.json <tool_api_file>` (about ten seconds, no model, nothing leaves this machine). It plays hundreds of calls with random extraction results and with customers who are stuck, and reports each defect once with the shortest call that shows it. Fix what it reports of NO_END, NO_CLOSE, REPEAT, STUCK, CODE_ERROR, ENUM_WRITE, NO_URL, BAD_CALL, GOODBYE, TEMPLATE, and run it once more. At most two rounds of this, then go on: the program that started you runs it again, together with test customers, and comes back to you with what is left. Do not write test scripts, drivers or simulations of your own and do not read its source; the time of this step is counted and the whole build has a limit. Read "Every call ends" below before you write `gen.py`, so that there is little to fix here. Its made-up customers carry made-up amounts and dates: fix the mechanism, never a value.
7. Go through `rules.md` line by line against the generated workflow and confirm each rule is present. Fix what is missing.
8. Finish with one line: `BUILT slot=<slot>`.

Do not save the workflow to the platform, do not run `smoke.py`, an export, simulations or `run_cases`. The program that started you checks and tests the workflow after you finish, may come back to you with defects to repair, and saves the final version itself. The platform can take minutes to answer; nothing in your steps should wait for it.

`reference/example_generator.py` is a generator that produced a passing agent for one particular brief. Use it only to see working shapes: an `api_call` tool, `response_mapping`, pre and post hooks, a code step, a closing chain. Its rules, sentences, numbers, holidays and outcome table belong to that brief. Do not carry any of them over. Three things in it you must not copy: it starts with a code step; it lets the model send the customer's values to the bank itself; and its pre hooks stop a call by setting `config['url'] = ''` (see "The engine sends what the customer said" below for what that does on the platform).

## Which mechanism enforces which rule

Prefer the highest row that can carry the rule. A rule left to the prompt holds most of the time; a rule in the engine holds every time, and every customer must pass three times.

| Rule kind | Mechanism |
|---|---|
| "X only after Y" (no account data before identity, no promise before confirmation) | Put the tool only in the step reached after Y. Gate the step change on a variable set from Y's tool result. |
| A sentence that must be said, word for word | `on_enter` of type `tts` with the fixed text on the step entered when its condition is met. |
| A sentence that must not come before an event | Keep the word out of every prompt and fixed text of the steps before the event. |
| A count or limit (attempts, wrong answers, offers, a question asked once) | A counter variable changed in code or a tool hook, and a deterministic transition on it. Never the model's memory. See the next section. Add `max_node_turns` with `max_turn_transition` as a backstop. |
| A date or amount calculation (deadlines, business days, holidays, minimums, bands) | Python, from the call's `now` variable and the account data. Never the real clock, never the model's arithmetic. Give the model the finished facts as text. |
| A value the customer said that goes to the bank (a security answer, a date, an amount, a time) | Extract it from the customer's message, check and complete it in a code step against the computed facts, and let the engine make the call (`api_request` step) only when it is complete and allowed. The dialogue model does not hold that tool. See "The engine sends what the customer said". |
| What the agent says next, when code already knows it (an offer, a read-back, a refusal of a value, a question for the missing part) | Fixed text built in the code step and spoken by the engine. Never a prompt that tells the model "do this, otherwise that". |
| Which outcome and reason close the call | One closing step per outcome/reason pair, run by the engine (`api_request` with the closing call in `pre_actions`), reached by a transition on a variable. |
| Choosing a branch from what the customer said | An extraction variable with `enum_values`, then `equals` transitions. More reliable than several competing `matches_intent` transitions. |
| Tone, sympathy, short answers to side questions | The step's `task_message`. |

## Counts, single offers and closings

These are the defects that independent reviews and test calls found again and again in generated agents. Each one fails a customer in some of the three runs. Build them out from the start.

- **The model never keeps a count.** No prompt may say "track", "count", "remember how many", "ATTEMPTS USED", "for the second time" or "only once in the whole call". The engine cannot see what the model said freely, so it counts events it does see: a tool result (count in the post hook), an extracted value of the customer's last message (count in a code step the transition passes through), or the entry into a step.
- **One reply-kind value per stage.** In every step where the brief treats customer reactions differently, extract ONE enum variable from the customer's last message. Its values cover every reaction the brief names for that stage, each described so that two values cannot both fit: for a negotiation stage that is for example a flat refusal, a non-answer or evasive reply, a date, an amount, "too much", acceptance, hardship, a dispute, "already paid", not wanting to talk, a request for a person. Do not use several independent extractions that must agree, and do not let a catch-all value such as "other" swallow a reaction the brief has a rule for. Where a specific reaction is also an instance of a general one (the person on the line reports a death, and is also "someone else"), say in both descriptions that the specific one wins, and test it first. Route with `equals` on this variable.
- **The default branch changes nothing.** When the reply-kind value is the catch-all, when a statement names no item, or when a yes or no names an item other than the one the open offer is about, the code step does not treat it as a refusal or an acceptance of the open offer. It leaves every counter and every agreed value as it is and asks the open question again. Seen on the platform: a "yes" about one item accepted the open offers of all items; an invented second "no" with no item used up another item's only attempt; a "no" at the read-back that contradicted nothing dropped every agreed promise. A value already agreed is given up only when the customer clearly withdraws it.
- **A counted reaction passes through a code step.** The transition for a counted value goes to a small passthrough code step that increases the counter and writes what happens next (the next offer, or a flag that the limit is reached), then continues with deterministic transitions: back to the conversation step, or to the closing step when the limit is reached. A counter that belongs to one item of several (one product, one question) is a variable per item.
- **A closing that depends on a count is taken by the engine.** "After the second unclear answer", "after the second refusal", "when the attempts are used up": a `greater_than` or `equals` transition on the counter leads to the closing step. Do not leave such a closing to a tool the model may or may not call, and do not use `matches_intent` for it.
- **An offer or question the brief allows once is said by the engine.** Put it as fixed text on entering its own step, or set a flag variable in the same code step that decides to make it, and never offer it again while the flag is set. This holds for every "once" in the brief: a single lower offer, a single request for an exact value, a single request for another time, a single "can I help first".
- **A question the brief counts is asked whole, in one sentence.** Where the brief says a question is asked once (or twice), every part of the answer is asked for in that one sentence: "On which day and at what time can we reach you?", never "When can we call you back?" followed by "At what time?". The judge counts sentences, not purposes. Seen on the platform in the agents of three separate builds: the customer gave only the day, the agent asked for the time, and the check "asks exactly once for another time" failed with the bank records right. So when the answer to a counted question comes back with a part missing, the follow-up for the missing part IS the next counted ask: it adds to that question's counter, and when the counter is at its limit the call takes the brief's closing for it instead of asking. The same holds for an offer the brief allows once: one other date, one lower amount. A second date for the same item is a second offer.
- **Something the customer says in between does not change a count.** A question back, a repeated request the agent may not grant, a change of subject, a value given in two parts: the agent answers shortly and the stage continues where it was. Such a turn must not start a new attempt, repeat a counted question, or reset a counter. Give these reactions their own reply-kind value that leads back to the same step without touching the counters.
- **No global instruction may contradict a step.** A sentence in the system prompt applies everywhere. If the brief says "answer the question, then ask again" in one stage, a global "do not repeat your question" breaks it. Keep the system prompt to identity, tone and honesty; put ask-again behaviour in the step, as fixed text where it is counted.
- **A write that needs the customer's yes is gated on that yes.** When the brief allows a tool call only after a read-back and a clear confirmation, extract the confirmation as its own variable in that step, and let the transition to the engine step that makes the call fire only on that yes. Checking only the values is not enough. A yes to an offer is not a yes to the read-back.
- **Turned-down values and failed calls are different counts.** A value the code step turns down for a rule (a time outside a window, an amount below a minimum) is counted under that rule's own counter and never reaches the bank. A value that is incomplete or badly formed is asked for again without counting. A service failure counts as a failure. Every retry has a limit taken from the brief; where the brief gives none, one retry, then the agent says plainly that it could not do it. Nothing may tell the model to "try again" without a counter.
- **With several items, one customer sentence can treat them differently** ("the card tomorrow, not the loans"; "I paid the first one, the other I won't pay"). A single reply-kind value with a single scope cannot hold that: seen on the platform, "all" turned one item's date into a promise for every item, and one item's dispute was noted on all of them. Extract per turn which items each statement applies to (a list of item ids or "all") separately for what is accepted, refused, disputed or reported paid, and apply each statement only to its items.
- **With several items, the engine holds each item's end state.** When a call handles several items that each end in their own way (promised, refused, disputed, paid, failed), write each item's end state to a variable when it is decided. Derive the per-item tool calls and the closing outcome and reason from these variables in code, not from the model's reading of the conversation.
- **With several items, one sentence can carry as many statements as there are items.** If a call can cover up to N items, the extraction of one turn has room for N separate statements, each with its own kind, its own items and its own date and amount. Seen in test calls: with room for two, the third statement of "I pay the first today, the second is already paid, the third is not mine" was lost, its note was never written and the call never closed. "The others" means the items no earlier statement of the same turn named.
- **"I can pay" is not "I have paid".** Where the brief treats a payment the customer says was already made, the variable that holds it is filled only by a statement about the past ("I paid it on Wednesday", "that went out last week"). Say in its description, with examples, that "I can pay it today", "I will pay all three", "I can pay the full amount" are offers for the future and leave it at `none`. Seen on the platform in one agent, twice in thirty calls: "Yes, I can pay the full amount today" was answered with "On which date did you make that payment?" and noted as already paid, and a cut-off "No, but I can pay all three" sent all three products to the payments team. In code, an already-paid claim never wins over a reply kind that accepts or proposes a payment in the same message.
- **A value that was computed from another value is computed again when that one changes.** Seen: the customer chose direct debit, the agent moved the date by the two business days the brief asks for, the customer switched to the app to pay today, and the read-back kept the later date. When the channel, the product, the amount or the day changes, derive again everything the brief ties to it before the read-back.
- **A reply to an offer the agent just made belongs to that offer first.** When the agent has asked a yes-or-no question of its own (shall I connect you to a team, can you pay this amount on this date, may I help you first), the engine holds which offer is open in a variable, and the code step looks at that variable before any general reply-kind branch. Seen in two independently built agents: the agent offered to connect the customer to one team, the customer said "yes, please connect me", the classifier labelled that as a request for a person or for a new plan, that branch ran first, and the transfer went to the wrong queue with the wrong closing reason. An acceptance or refusal of an open offer with no new fact in it is never routed by its general label. Describe the general labels so that accepting what the agent just offered is a yes, not a request.
- **"This rule comes before rule N" holds on every turn of that path, not only on the first reply.** When one customer message can carry two signals the brief ranks (a hardship and a request, a hardship and a date, a dispute and an amount), extract each signal as its own variable and apply the brief's order in one place in the code step. Do not let whichever label the classifier picked decide. What the higher rule demands (a fixed sentence, no persuasion, a particular offer) is still done when the lower signal is the one being handled: if the customer mentions a hardship and names a date in the same sentence, the required sentence is said before the read-back. A flag keeps a sentence the brief allows once from being said twice.
- **A side question in the same message as the answer is still answered, in every step.** Customers on the platform put both in one message ("my salary comes on the sixth, I can pay then. Am I talking to a robot?"), in the middle of a negotiation as well as at the opening. One reply-kind value keeps only the main answer, and when the engine then speaks a fixed sentence the question is dropped; the judge fails the call although the opening already said it and the bank's records are right (seen in 7 platform calls, in three independently built agents). In EVERY conversation step that waits for the customer, extract an enum variable whose name starts with `side_q` (`side_q`, or `side_q_<step>` if you need them apart), independent of the reply-kind value. Its members are the questions the brief gives an answer for (is this a robot, is this a scam, a question the tools cannot answer, ...) and `none`. The code step that handles the turn puts the brief's answer sentence in front of whatever the engine says next. It changes no counter and starts no new attempt. A robot question is never a request for a person: say so in both descriptions. **A message that is only a question is not a refusal and not a wrong answer.** Seen: at the second security question the customer asked "Which account is this about?", the reply kind came back as `refuse`, it was the second one, and the call was closed as a refused identity check. In the code step, when `side_q` is not `none` and the message carries no value for the open question, answer the question, ask the open question again, and change no counter, whatever the reply-kind value says. Say in the description of the refusal member that a question back is not a refusal.
- **What the customer said for all items is kept for each item.** When a call covers several items and the customer names one day or one amount "for all" or "for both", write it to a variable per item in the turn where it is said. Every later offer and read-back for an item is computed in code from that variable and the item's own limits (for example the earlier of the customer's day and the item's last allowed day, with the brief's sentence about it), whatever the item's position in the list. After the customer has named a day, no item gets the default first offer. Seen on the platform: the reply had no field for the day, the first item got the customer's day, and the second item was offered and recorded on the agent's default day.
- **A sentence owed on the turn that ends a stage is still said.** When the turn that settles the last item, or that leads to a closing, also owes the customer a sentence from the brief (a fact about a payment, an apology, where to turn), the code step keeps it in a variable and the closing chain says it in front of the closing text.
- **After a record is made there is a customer turn only if the brief has a rule for what comes after it** (a request to change the record, to cancel it, for something else). Then that step says the brief's sentences, adds no question the brief does not ask for, has `max_node_turns` 1 or 2 with `max_turn_transition` to the closing chain, and every reply the brief has no rule for leads to the closing chain.

Keep it small: one conversation step per stage with its reply-kind value, one code step per counter, one closing step per outcome and reason. More steps than the brief's rules need are more places to fail.

## Every call ends

Measured on the platform: one failed call in five never reached its closing call. The agent asked the same question 47 to 77 times ("Which day do you mean?", "Please tell me the full year of your birth", "Am I speaking with ...?") until the time limit, because the extraction kept returning something the code could not use and nothing counted. `fuzz_workflow.py` plays exactly these customers. Build so that it finds nothing:

- **`max_node_turns` does not protect a step that every customer message leaves.** When each message goes on to a code step and the code step comes back, the step's turn counter starts again at every entry and never reaches its limit. In that shape the limits live in code.
- **Every sentence that asks again has a counter and a way out.** Wherever code can send the same question twice (a value it could not read, a part that is missing, a reply of the wrong kind, a cut-off message, a catch-all reply), it counts how often in a row, and at the limit it leaves through one of the brief's closings: the one the brief gives for a customer who does not answer or cannot be understood at that stage. The limit is the brief's where it has one, three in a row where it has none. A complete, usable answer resets the counter.
- **One counter of all customer turns.** The code that handles each message adds one to a single variable; past a limit that no real call of this brief reaches (about 40) the call goes to the closing the brief gives for a call that could not be completed. This is the last backstop, not a rule of the bank.
- **A customer who says goodbye is answered by the closing chain** of the stage the call is in: its closing call, the closing sentence, the end of the call. Give every reply-kind enum a member for it. The agent never asks its question again after a goodbye.
- **A value kept from an earlier turn is never read as the answer to this turn.** When this turn's extraction gives nothing new for the open question (the platform drops a value it is not sure of, and the old value stays in the variable), the code does not act on the old value again: clear each answer variable to its neutral member once it has been used, and treat "nothing new" as a reply that could not be read. Seen in recorded calls played again with one empty turn put in: the promise was recorded for another day, a note got another reason.
- **Every path from the opening reaches the closing call, and the closing call is made once.** Also when a tool fails, when the identity check ends, when the customer hangs up in words.

## What the platform's models do differently

Seen in calls on the real platform. The phone agent's model there is weaker than the one that writes this workflow, and the judge reads more literally.

- **The model must not decide whether an answer is good enough, and must not send it.** Seen: the model heard a full date of birth and asked the customer "for the full year" instead of using it; in another call it heard half a date, made up the year and sent it, and one of the allowed wrong answers was gone; in a third it "corrected" the order of a date said in numbers, so the sentence the brief demands for that case was never said. What the customer said is taken by the extraction, and code decides. See "The engine sends what the customer said".
- **The model picks the wrong one when a prompt gives it two ways to go on.** Seen: code had decided that the read-back comes next, the step's prompt still said "otherwise continue with the next item and its first offer", and the model made a second offer for an item the customer had refused, with an amount that was in no computed fact. Once code knows the next sentence, the engine says it as fixed text.
- **The model offers things nobody asked for** when a prompt leaves room ("shall I set a reminder", "would you like me to note that"). Every such sentence is an offer outside the brief and a question the judge can count. In steps where the engine decides what is said next, give the model the exact sentence to say and tell it to say nothing else.
- **A label the classifier gives can differ from run to run for the same sentence.** Where one customer sentence can carry several facts ("I can pay all three on Friday"), do not rely on a chain of several classified turns to rebuild it. Extract the facts themselves (which items, what date, what amount) in the turn where they are said, and compute from those.
- **The customer's message can stop in the middle of a sentence.** Seen in many platform calls; with talkative customers up to 19 of 24 messages of one call: "I can pay on the twenty", "My date of birth is the", "Yes, but the car loan I". Such a message is not an answer. It is not a refusal, not a wrong answer, not silence and not a vague period, so it moves no counter and uses up no attempt, and a value cut off inside it is not sent anywhere. Every reply-kind enum has the member `broken_off` ("the message breaks off before the answer to the open question is complete"). The code step handles it like this: keep whatever is usable in the message (an item named, a "not today", a part of a number); the first time in a row, say one fixed sentence that asks the customer to say it again; the second time in a row, do not ask the same open question again but a narrow one that a single word answers ("Can you pay it today, yes or no?", "Which day of the month?"), built from the open question. Count the repeats in a variable that is reset by any complete answer; after the brief's limit for non-answers, or after three in a row where the brief gives none, treat it as the brief treats a non-answer.
- **A message that has nothing to do with the open question is not a refusal.** A talkative customer says a sentence about the weather or the office before the answer. Give it its own reply-kind member, apart from refusal. What it costs follows the brief's rule for non-answers; where the brief has none, the open question is asked once more without counting.

## The language of the call

The brief says which language the calls are in; when it does not, they are in English. Everything the customer hears is in that language: every fixed sentence in `gen.py`, every `task_message`, the answers to side questions, weekday and month names in read-backs, amounts and dates as that language says them. Write the sentences the brief gives word for word; translate nothing the brief gives in the call's language, and do not mix languages in one sentence. The customer answers in that language too: say so in every extraction description and give the examples in it (the yes and no words, the ways to say a date, a time, an amount and digits one by one, the words for "today", "tomorrow", weekdays and months, the usual ways to refuse, to ask for a person, to say goodbye). Code that reads a value knows the number words, weekday and month names of that language, with and without its special letters ("çarşamba" and "carsamba"), and lower-cases with the language in mind. Names of variables, steps and enum members stay in English. `rules.md` and the reports stay in English. Put three sentences of the call's language into `selftest.py` for each kind of value code reads.

## Rules of construction

- **Do not start with a code step.** The chat test route skips an initial code step, so its variables are missing there. Start with the opening conversation step. Compute calendars and other facts in a code step that is entered later, just before the first step that needs them.
- **One code execution per customer message.** On the platform every code step is a separate run in a sandbox, and the customer waits for all of them: measured in agents built with this skill, 8 to 12 step changes after one message, a median of 10 to 20 seconds before the agent spoke, and customers who hung up while waiting (the call then has no closing record and fails twice). After a customer message the path to the agent's next sentence is: one code step that decides everything, at most one bank call, the step that speaks. A result that needs code again (a bank answer) gets one more code step, not a chain of them. Do not route through a dispatcher step and then a handler step and then a finalising step: one step does all three. `fuzz_workflow.py` prints "Most step changes after one customer message"; keep it at 5 or below.
- **A code step that could not run is run again; it never closes the call.** The platform's Python sandbox drops single runs (`function_call_error: Failed to reach snekbox: Connection reset by peer`). The code then did not run at all, no variable was written, no transition matches, and the step leaves by its `passthrough_default_transition`. Seen: that default led to the closing step, and two of thirty customers were closed as unreached right after "Yes, that is me". Give every code step two retry copies: the default of the step leads to a copy with the same code and the same transitions, its default to a second copy, and only the second copy's default leads to a closing. `check_workflow.py` refuses a code step whose default reaches a tool call or the end with fewer than two retries. The same holds for a code step after a bank call.
- **Every extraction variable that code writes is a string or an enum.** The platform checks what code writes to an extraction variable against the variable's type and silently keeps the old value when it does not fit (`validation_errors: variable 'd_day' rejected by schema validation`). Seen: `d_day` was an integer and `amt` a float, code cleared them with `''` after each turn, the platform kept the old day, and every later "Yes, I confirm" was read as the old date proposed once more: the offer was repeated, then counted as refused, and two of ten customers failed all three runs. The local test did not show it. Declare a value the customer says (a day, an amount, digits) as type `string` and parse it in code; clear it with `''`. Clear an enum only with one of its members (`none`). Better still, do not rely on clearing at all: copy what the turn needs into your own variables and decide from the reply-kind value whether this message carried a new value. `fuzz_workflow.py` reports such a write as ENUM_WRITE.
- **No `global` in workflow code.** The platform runs a code step inside a function, not at module level. A top-level `st = {}` and a function that says `global st` are then two different objects: the function fills one, the last line saves the other. Seen: the saved state lost the stage and the current identity field after every turn, the postcode was sent as the birth year, verification looped up to 160 times, and 27 of 30 customers failed, while the same file passed the local test of that day. Make every piece of state one dict (or list) at the top of the code and only change it in place inside functions (`st['k'] = v`, `st.clear()`, `st.update(...)`); never assign to a top-level name inside a function. `check_workflow.py` refuses `global`, and the local engine now runs code the way the platform does.
- **Never write `None` to a variable that a tool call sends.** Seen: code set the field variable to `None`, the request went out without that field (`missing field field`), the answer was an error, and the step was entered again, 8 to 161 times in one call. A variable that fills a request body always holds a text. And cap it: a code step that sends the call to the same tool step three times in a row without a customer message in between closes the call with the brief's outcome for a failed service instead.
- **`min_confidence` is set on every extraction variable, to 0.3 or lower.** Never leave it out: the platform's default is 0.95. Measured on the platform: right answers come back with a confidence of 0.50 to 0.60 ("Yes, I confirm." 0.53), and with a threshold of 0.5 or 0.6 some of them are dropped silently (`extraction_failed ... low_confidence`), the variable keeps its old value and the agent asks again. `check_workflow.py` refuses a higher value.
- **One customer sentence, one meaning.** The platform fills the extraction variables of a step with separate model calls, and they do not agree with each other: "Yes, I can pay it today" gave `kind = yes` from one and `paid_items = this` from another. Put meanings that exclude each other into ONE enum, and in code let the answer to the open question win over any side flag.
- The sandbox is also slow. Use few code executions per call. Wrap code in `try` and leave safe defaults so the call can still close with the right outcome. Initialise every counter and flag where it is first needed and treat an unset variable as its default in conditions (`is_not_set`).
- **A list or an object in a tool result cannot be mapped to a variable.** A `response_mapping` whose path ends at a list or an object (`data.products`, `data.account`) sets nothing on the platform: the variable does not exist afterwards. Seen: the code waited for the mapped product list, counted a failed call, called the tool again and closed the call as a service error; 8 of 10 customers, three runs out of three, while the local test of that day passed. What exists after a call are the leaves, under the name of the STEP that made the call, not the tool's name: `<step name>_response.data.products.0.past_due` = `420`, `<step name>_response.data.ok` = `"true"` (booleans are the texts `true` and `false`, null is the text `null`, numbers may arrive as numbers or as text: convert with care). These keys are merged and never cleared: a key of an earlier answer that the new answer does not have is still there, so decide from a field every answer has. A bank error arrives as a normal answer with `data.ok` = `false`: test `data.ok`, not the HTTP status. Map single values (a flag, a count, an id) and read every list in the code step by walking those keys from index 0 until one is missing; convert the strings to numbers in code. The local engine now does the same.
- Route on tool results and variables. A step change that depends on a tool result uses that result's mapped variable. Booleans arrive as `"true"` or `"True"`: test both or write your own string flag.
- One step per stage with its own strict rules (who is on the line, identity, stating the debt and negotiating, after the promise, each closing). Keep optional actions of one stage together in one conversation step with several tools.
- **The engine sends what the customer said.** A tool call that carries a value from the customer (a security answer, a callback day and time, a promise date and amount, a reason) is not given to the dialogue model. The conversation step extracts the value from the customer's message, a passthrough code step checks it, and only a complete and allowed value goes on to an `api_request` step whose call the engine makes from variables; its result is mapped to variables, and the next sentence is fixed text chosen from them. Everything else (a part missing, a value the brief does not allow, a question for another value) ends in a fixed sentence and the same conversation step, with the right counter changed in code. Two independently built agents each failed their first tests for the same reason, a callback time the brief does not allow that still showed up as a tool call, and both repairs ended with this shape.
  - **Never stop a call inside a hook.** A pre hook that sets `config['url'] = ''` (or removes it) does not cancel the call: the platform reports `function_call_error: Missing required field: url`, the post hook does not run, the sentence the hook prepared is never said, and the model invents one ("I am sorry, I encountered a technical issue"). Seen in every agent built so far, 3 to 4 times per call with a customer who gives digits in two parts. A hook may normalise a value; whether the call happens at all is decided by a transition before it.
  - **A value in parts is put together in code.** Customers say a number in two parts over two turns ("463", then "51"), or a date as day and month first and the year later. The extraction takes what this message contains, exactly as said and with nothing added. The code step knows the full shape of each field (how many digits, which parts of a date), keeps the part in a variable, joins it with the next part, and sends the value once it is complete. An incomplete value changes no counter; the fixed sentence says what was heard and asks for the rest ("I have six six. What are the remaining digits?"). Only a complete value that the bank rejects counts as a wrong answer. A corrected value ("... no, sorry, ...") replaces the parts kept so far.
  - **This holds for every value and at every point, also after a hint and after a cut-off message.** Platform customers split even a year: "19...", then "86"; "Twenty.", then "oh eight." Seen in two agents built with this skill: the first half was taken as a cut-off message and thrown away, the second half ("86") was sent as a two-digit year, the bank answered with its hint, and the call ended as a failed identity check; in another the half "19" went to the bank and was counted as a wrong answer. A part is never sent, never counted and never thrown away: "19" is not a year, it is the first half of one. Keep it when the message is cut off too. After the bank's hint the next answer is read like any other: when it completes the value, send it. **A field that is not in every response keeps its old value on the platform, whatever code wrote in between.** Measured: code set the hint variable to `none` before the call, the bank's answer had no `hint` (`verified: true, all_verified: true`), and after the call the variable held `four_digit_year` again, from the call before. The agent asked a verified customer for four digits 21 times. So after every call read first the fields that every response has (verified, all verified, ok), and look at an optional field (a hint, an error code, a reason) only when those say the call did not succeed, and then only if it fits the value you just sent: a hint that asks for four digits after you sent four digits is left over, and the answer is a wrong answer like any other. Clearing the variable in code is not enough. The model-free test's engine does the same as the platform here. The program that started you replays your test calls with every number split over two turns and reports each call whose bank records change.
  - **Where the brief fixes how a value is read, code reads it.** When a value can be read in two ways and the brief says which one holds (a date given only in numbers, a relative day such as "next Friday", a time without am or pm), extract what the customer said in the order it was said (the numbers one after another, the words), and build the bank's format in code by the brief's rule. Do not ask the extraction for the finished ISO value: the model will pick the reading that looks right, and the path the brief describes for the other reading never runs.
  - **Numbers reach code as digits.** Customers say values in words ("nineteen October nineteen eighty three", "four four one zero", "five hundred and ten"). Tell the extraction, in the variable's description, to write every number that was said in digits and to change nothing else ("19 October 1983", "4410"): no digit added and none dropped. Give only plain examples of whole values. Do not put a rule about short or partial values into a description: seen twice, in both directions. Without any guidance "Eighty-one" came back as 1981 and the brief's question for the four-digit year was skipped; with the sentence "'eighty-one' is '81', never '1981'" in the description, the full answer "eleven August nineteen eighty one" came back as "11 August 81", the code rejected it twice and the call closed as not verified. What a short answer means is decided in code, and a part that was asked for again is accepted as the bare answer it is: the extraction model does this reliably, a number-word parser written in a hurry does not. Seen: the raw words went to code, code read the first "nineteen" as the century, said "I have October 1919. What is the day?", sent 1919-10-19 three times, and the call ended as a failed identity check in two of three runs. Code still has to cope when words arrive anyway: put that sentence and two more of its kind (a date, a digit string, an amount, each in words) in `selftest.py` and make them pass.
  - **No code in hooks.** A pre or post hook of a tool call is one more sandbox run, and when it is dropped the call goes out with the raw template values (seen: `amount` sent as the string "510.0" after `Failed to reach snekbox`, the promise was booked twice and then noted as a service error). Build the finished body in the code step before the call and let the `api_request` step send variables as they are.
  - A value of the wrong kind for the open question (four digits when a date was asked) is never turned into a plausible one. The fixed sentence says what is needed.
- **Every body field of an `api_call` tool has a `default`.** In a call the engine makes, each field's default is `"{{<variable>}}"` with the variable your code has just written, or a fixed value. Measured on the platform: a body field with no `default` never reaches the request and the call fails. If a tool does stay with the dialogue model (only where the brief has no rule at all about the values it carries), a field the model fills gets a placeholder default `"{{<tool>_<field>_in}}"` whose variable nothing ever sets: no extraction variable, no code, no `response_mapping` target, no call variable; a placeholder whose variable holds a value sends that old value and hides the parameter from the model.
- **An extraction variable with `enum_values` only ever holds one of those values.** When code resets such a variable, it writes a neutral member of the enum (give every enum a `none`). The platform rejects any other value, also the empty string, and keeps the old one, so a transition fires again on a stale reply. Seen in 17 of 24 failed platform calls.
- A model in a step can call only the tools listed in that step. Give each step only the tools its stage allows.
- In `task_message`, write instructions for that step only. Do not describe routing or name other steps. A step whose replies are handled by extraction and code tells the model only how to answer shortly and what it must not say; it names no tool. Tell the model to never end a turn with nothing.
- Dates: do not use extraction type `date` for a customer's payment date; the platform resolves vague dates with its own clock. Extract the day as the customer said it (a day of the month, a month, a weekday, a relative word) and resolve it in code against a calendar computed from `now` (weekday, date, allowed or not, and why). A vague period ("next week") is not a date: ask once for the exact day.
- Tool failure: the agent says plainly that it could not complete the action. Whether it retries, how often, and how the call closes then come from the brief.
- Every path reaches the end of the call through exactly one closing call, and the closing call is the last tool call. The model should not be able to call the closing tool twice. After the closing step go straight to an `end_call` step.
- The closing sentence is the only place where the agent says goodbye. Put it on the closing chain as fixed text.
- Use every tool field name and allowed value exactly as in the tool API file, and its server URL. Call no other host.
- No `null` anywhere. Leave `agent_config` out. A prompt variable that may be unset must not sit in a fixed spoken sentence.
- Keep `gen.py` deterministic: the same inputs give the same workflow.
